# Сеть Miniforge — выбор транспорта и план работ

## Какой режим выбрать

| Режим | Где запускать | Как проходит трафик | Как проверить |
|---|---|---|---|
| `singleplayer` | Редактор, Web, Desktop | Сетевого трафика нет. Подходит и для игры с экраном выбора лобби до ручного вызова `api.net.connect()`. | Обычный **Play**. |
| `local-splitscreen` | Редактор, Web, Desktop | 2–4 локальных игрока, один экземпляр игры. | **Split-Screen Co-op 3D**, обычный **Play**, отдельные раскладки или геймпады. |
| `client-server-ws` | Web и Desktop | Node.js-ретранслятор или встроенный Desktop LAN. Сервер принимает участников, разделяет комнаты и пересылает пакеты. | **Multiplayer Arena 3D**, два клиента и отдельный реальный relay. |
| `p2p-webrtc` | Web и Desktop с поддержкой WebRTC в браузере или WebView | WebSocket принимает игроков в комнату и передаёт сигнализацию. Для каждого получателя пакеты идут по открытому DataChannel или по WebSocket, пока прямой канал недоступен. Для публичного адреса используется STUN, TURN пока не настраивается. | **WebRTC Arena 3D**, клиенты в разных сетях. Успешный RPC подтверждает доставку. Чтобы доказать прямой маршрут, проверьте состояние DataChannel через средства диагностики браузера. |
| `steam-p2p` | Desktop-редактор через **Play with Steam**, Desktop-депо через Steamworks | Steam Lobbies для списка и владельца комнаты, Steam Networking Messages с доступом к Steam Datagram Relay для пакетов. Node.js relay не нужен. | **Steam Relay Lab**, два аккаунта с одним AppID, проверка **Relay status** и **Ping peer**. Подробности в [руководстве Steam](STEAM_NATIVE.md). |

`url: "local"` и **Project → Multiplayer & Net Debugger → Launch Host + Client** используют локальный обмен сообщениями в редакторе. Это быстрый тест логики двух клиентов, задержки и потерь. Для Steam используется отдельная **Local Debug Simulation**. Чтобы диагностировать реальные WebSocket, WebRTC, LAN или Steamworks, запускайте соответствующий транспорт. [Инструкции к проектам-примерам](NETWORK_EXAMPLES_3_0_4.md)

## WebSocket и LAN

Запустите Node.js relay из корня репозитория.

```bash
node server/relay-server.mjs 8765
curl http://127.0.0.1:8765/health
```

По умолчанию relay слушает только `127.0.0.1`. Для второго ПК в доверенной LAN укажите доступный интерфейс или `0.0.0.0` вторым аргументом, а в настройке клиента используйте IP хоста. Для Web-игры по HTTPS настройте `wss://` через TLS-прокси с поддержкой WebSocket Upgrade. `/health` показывает число подключений и комнат. Комнаты живут в памяти процесса.

`api.net.connect({ mode: 'client-server-ws', url, room, token })` возвращает успех после подтверждённого входа в комнату. При отказе используйте `getLastError()`. Опциональный `MINIFORGE_RELAY_TOKEN` проверяется при входе и подходит для закрытого теста. Токен, встроенный в открытый клиент, доступен игрокам. Node relay ограничивает комнату 32 участниками по умолчанию, принимает текстовые пакеты до 256 КиБ и ограничивает частоту отправки. `settings.multiplayer.maxPlayers` пока не задаёт лимит отдельной комнаты на Node или Rust relay.

В экспортированной Desktop-игре хост может включить **Auto-start embedded LAN server** или вызвать `api.net.hostLan({ port, room, gameName })`. По умолчанию игра слушает TCP `8765`, поиск соседних игр использует UDP `41234`. Клиент может прочитать `url` и `room` из `api.net.discoverLan(1400)` или ввести адрес вручную. Встроенный LAN-релей предназначен для локальной сети. Текущий **Play with Steam** передаёт кадру игровые Steam-команды, поэтому проверяйте нативный LAN API в Desktop-игре.

## Скрипты, Event Graph и игровое состояние

| Задача | Script API | Event Graph |
|---|---|---|
| Подключить игру и показать состояние | `api.net.connect()`, `disconnect()`, `isConnected()`, `getLastError()`, `getPeers()`, `getStats()` | `net.connect`, `net.disconnect`, **Network Status** |
| Передать действие или чат | `rpc(name, payload, target)`, `onRpc()`, `sendChat()`, `onChat()` | `net.sendRpc`, **On Net RPC**, `net.sendChat`, **On Net Chat** |
| Поднять и искать LAN-игры | `hostLan()`, `discoverLan()`, `stopLan()` | **Net Host LAN Server**, **Discover LAN Games**. Остановку вызывает скрипт. |
| Обновить выбранное поле Network Sync | `setSyncedField()`, `getSyncedField()` | **Write Network Sync Field**, **Read Network Sync Field** |
| Следить за присутствием игроков | `onPeerJoin()`, `onPeerLeave()`, `peerId()`, `isHost()` | `event.peerJoin`, `event.peerLeave`, `net.peerId`, `net.isHost` |

У асинхронных нод с **Started / Completed / Failed** обновляйте UI по **Completed** или **Failed**. **Started** означает, что запрос запущен. При подписке из скрипта храните функцию отписки и вызывайте её в `onDestroy()`.

Компонент **Network Sync** синхронизирует выбранные поля, трансформы, анимацию, активность сущностей и поддерживаемые сценарии спавна и удаления. `owner: "local"` создаёт отдельные прокси для игроков. `owner: "host"` передаёт авторитет для общей сущности хосту. Для Steam текущий хост определяется владельцем лобби. У остальных транспортов роль определяется сортировкой peer ID. Смена роли не гарантирует восстановления состояния матча. WebSocket пытается переподключиться до пяти раз после обрыва уже принятого соединения. Возврат соединения сам по себе не гарантирует продолжение матча. [Настройка Network Sync](UNIVERSAL_NETWORK_SYNC.md)

Relay подтверждает, что пакет пришёл от сокета, принятого в комнату. Игровые правила исполняются в клиентах. Например, в **Multiplayer Arena 3D** подбор предмета обрабатывает хост и проверяет дистанцию. Для соревновательной игры серверный процесс должен сам проверять действия и рассчитывать итоговое состояние.

## Что осталось

| Приоритет | Работа | Критерий готовности |
|---|---|---|
| P0 · Нативная приёмка | Прогнать Steam с двумя реальными аккаунтами на разных сетях. Проверить Desktop-редактор и депо, лобби и приглашения из запущенной и закрытой игры, обмен RPC/снимками, смену владельца, сеть после обрыва и сервисы Steam на своём AppID. Отдельно прогнать LAN discovery и реальный WebRTC на целевых ОС. | Матрица ОС и сценариев с результатами. Автотесты Local Debug и проверки IPC дополняют этот прогон. |
| P1 · Комнаты и вход | Общий UI лобби, состояние Ready/Start, настройки доступа и вместимость комнаты, управляемые на сервере. Для публичного Web задать схему авторизации, короткоживущие допуски, TLS, мониторинг и нагрузочный тест. | Три клиента видят одинаковый список и состояние. Полная или закрытая комната возвращает ясную причину отказа. |
| P1 · Обрывы и совместимость | Версия протокола и проекта при входе, отдельные состояния reconnect/resync, политика при уходе хоста. Для продолжения матча нужны снимок с номером версии, передача авторитета и проверка позднего входа. | После потери хоста игра либо восстанавливает согласованное состояние, либо завершает матч с явной причиной. |
| P1 · WebRTC через интернет | Настраиваемые ICE/STUN/TURN, диагностика маршрута по каждому пиру и проверка переключения на relay. | Явно виден используемый маршрут, проходят тесты прямого канала и принудительного TURN на двух сетях. |
| P2 · API и Event Graph | Подключить проектный флаг Steam Cloud к рантайму и добавить недостающие ноды для сервисов Steam, которые уже доступны из скриптов. | При выключенном облаке сохранение остаётся локальным. Граф может отобразить ошибку чтения Cloud или статистики. |
| P2 · Производительность | Измерить трафик, задержку и CPU с несколькими клиентами. Если профиль игры требует, добавить разделение надёжных событий и снимков, приоритизацию видимых сущностей, предсказание и коррекцию. | Для выбранного масштаба проекта есть бюджет трафика, задержки и контрольные сценарии потерь. |
| По требованиям игры | Выделенный авторитетный сервер, постоянное состояние матчей, серверная проверка команд. Для Steam при необходимости добавить выделенные серверы и аутентификацию сессионными билетами. | Сервер принимает решения об уроне, движении и наградах, а перезапуск следует заданной политике восстановления. |

Для небольшого Steam-коопа текущий API уже покрывает лобби, обмен сообщениями и синхронизацию. Ближайшая задача для такого проекта — нативная приёмка и понятное поведение при обрыве связи. Для публичного кроссплатформенного или соревновательного мультиплеера основные пробелы лежат в протоколе, серверных правилах и эксплуатации. WebRTC/TURN и Steam SDR можно развивать в текущем стеке.

## Проверки в репозитории

```bash
pnpm test:network
pnpm test:network-sync
pnpm test:examples
pnpm build
pnpm exec playwright test steam-relay-lab.spec.ts
```

Playwright проверяет два клиента Local Debug, Desktop-архив и жизненный цикл **Play with Steam** с подменой нативного IPC. Реальные Steam ID, маршрутизацию SDR и работу на двух сетях фиксируйте отдельно.
