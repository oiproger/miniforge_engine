Как пользоваться справочником

Для первого проекта начните с практикума по HUD или урока Key Vault. Разделы api.* содержат сигнатуры методов для скриптов. В разделах type приведены связанные типы, включая Tween. Каталог Event Graph показывает входы, выходы и значения по умолчанию. Для поиска по любой ноде или методу нажмите Ctrl+F.

Базовое руководство редактора описывает серию 3.0. Подробности текущего поведения сети, теней, декалей и GI приведены в тематических главах. Steam Relay Lab запускается в Local Debug или с нативным Steamworks через Play with Steam в Desktop-редакторе. Для проверки Steam Overlay и запуска через Steam используйте депо.

Живые префабы и синхронизация

Когда вы создаёте префаб из сущности (ПКМ в Hierarchy → Save as prefab) или с нуля (File → New prefab), каждый экземпляр на сцене получает ссылку properties.prefabId. После правок в Prefab Editor кнопка Sync instances обновляет геометрию, компоненты и дочерние объекты всех копий во всех сценах проекта, сохраняя их мировые позиции.

Террейн: слои, размеры и кисть Scatter

  • Неограниченные слои материалов: добавляйте любое число слоёв поверх базового (трава, асфальт, грязь, бетон). Ползунок Hard ↔ Soft для каждого слоя задаёт резкость границ смешивания.
  • Изменение размеров (Resize Terrain): быстрые пресеты 16м / 32м / 64м / 128м и ручной ввод ширины/глубины/сегментов с билинейной передискретизацией карты высот и весов всех слоёв.
  • Кисть Multi-Model Scatter / Erase scatter: выберите несколько моделей или префабов (деревья, кусты, трава, камни), задайте плотность, разброс масштаба, случайный поворот по Y и привязку к нормали — кисть автоматически расставляет объекты по рельефу террейна.
Глава 3Ассеты

Импорт 3D-моделей и Model Editor (v1.2–v2.1)

Встроенная конвертация через assimpjs WASM, настройка слотов материалов и нарезка одной дорожки анимации на отдельные клипы.

Miniforge хранит 3D-модели в бинарном формате glTF 2.0 (.glb) — самом быстром и компактном формате для WebGL2. При импорте других форматов редактор автоматически конвертирует их в .glb прямо на лету.

Трёхуровневый конвейер импорта

  1. Встроенный Assimp WASM (assimpjs): работает «из коробки» во всех сборках — в браузере, Windows, macOS и Linux без установки сторонних программ. Поддерживает .x, .fbx, .smd, .obj, .dae, .3ds, .ms3d, .b3d, .ply, .stl, .md2, .md3, .md5mesh. Вместе с моделью можно перетащить сопутствующие текстуры и .mtl-файлы.
  2. Чистый TypeScript-парсер .x → .glb (xToGlb.ts): мгновенный резервный конвертер для текстовых DirectX .x файлов со скелетом и анимациями.
  3. Нативный Assimp CLI (Desktop Tauri): дополнительный fallback в десктопной версии, если системный бинарник assimp доступен в PATH.
Экспорт обратно в .glb для правок в Blender

В заголовке Model Editor есть кнопка .glb — она сохраняет сконвертированную модель на диск. Удобно, если нужно поправить ориентацию осей или скиннинг в Blender и загрузить обратно.

Настройка материалов в Model Editor

На вкладке Materials отображаются все меш-слоты (Part #0, #1, ...) с числом треугольников, цветом и флагом наличия встроенной текстуры. Для каждого слота доступны два режима:

  • Назначение Material Asset проекта: выберите любой существующий материал из выпадающего списка или нажмите + New material, чтобы создать новый ассет на базе цвета слота и сразу привязать его.
  • Быстрые оверрайды встроенного GLB-материала: оставив Embedded GLB default, можно менять Tint color, Opacity, Roughness, Metalness, Emissive, Unlit, Pixelated и Double-sided, сохраняя оригинальную диффузную текстуру из файла.

Нарезка анимаций из одной дорожки (Timeline Slicer)

Многие модели (особенно из паков .x, .fbx, Mixamo или Source) приходят с одной длинной дорожкой, где подряд записаны все движения. Вкладка Animations решает эту задачу неразрушающе — сам файл .glb не перезаписывается, а описания клипов хранятся в asset.properties.clips и нарезаются рендерером при загрузке с точной интерполяцией границ (включая SLERP кватернионов вращения костей).

  1. Выберите исходную дорожку в Source track и удобную частоту кадров (24 / 30 / 60 fps) для отображения кадров.
  2. Прокрутите ползунок таймлайна до начала движения и нажмите [ Set Start, затем до конца — и нажмите ] Set End (либо введите точные секунды вручную).
  3. Включите галочку Loop range, чтобы зациклить воспроизведение строго внутри выделенного зелёного отрезка и точно подогнать стык анимации.
  4. Введите имя нового клипа (например, Idle, Walk, Run, Attack) и нажмите Add clip, затем Save changes.

Сразу после сохранения новые клипы появляются в выпадающем списке компонента Animation в инспекторе, в полях walkClip / idleClip у NavAgent и доступны из кода через api.animation.play(id, 'Walk') и api.animation.crossfade(id, 'Run', 0.2).

Глава 4Blueprints

Визуальное программирование: Event Graph (Blueprints)

Аналог Unreal Engine Blueprints: 65+ нод под всё API движка, переменные (Local / HUD / WorldState), Exposed Variables и кастомные функции.

Компонент Event Graph (type: "eventGraph") заменяет устаревшие линейные правила на полноценный нодовый граф, который хранится как переиспользуемый ассет type: "graph" (меню Assets → New Event Graph). Старые Event Rule сохраняют полную обратную совместимость.

  • Типизированные пины и провода Безье: белый exec (поток выполнения), красный boolean, зелёный number, фиолетовый string, золотой vec3, голубой entity (со встроенной 3D-пипеткой выбора объекта со сцены) и серый any.
  • Переменные (My Blueprint → Variables): три области видимости — Local (локально в экземпляре), HUD (vars) (автосинхронизация с интерфейсом) и WorldState (переживает смену сцен). Флаг Editable in Inspector выводит переменную прямо на сущность для переопределения.
  • Кастомные функции (Functions): создавайте собственные функции с произвольными входными и выходными параметрами (Function Entry → логика → Return) и вызывайте их из основного EventGraph или других функций через ноду Call Function().
  • Покрытие всего GameAPI: события жизненного цикла, Branch / Sequence / ForLoop / Delay / DoOnce / FlipFlop / Gate, математика/векторы, Player / Camera / Physics Raycast, Play / Crossfade Animation, NavAgent, Get Surface Material At, свет, частицы, декали, Tween Move To, звук, UI, сохранения и реклама платформ.

Как устроен Event Graph внутри (интерпретатор, не компиляция в JS)

Event Graph не компилируется в JavaScript — в рантайме работает интерпретатор графа (packages/runtime/src/eventGraph.ts → createEventGraphLifecycle). Граф хранится в проекте как чистый JSON-ассет типа graph и не использует eval/new Function, поэтому без проблем проходит строгий CSP на веб-порталах (Яндекс Игры, Poki).

  • Поток выполнения (белые Exec-пины): распространяется вперёд от красного Event-узла через runFromPin() с защитой от бесконечных циклов (MAX_STEPS = 2000, MAX_CALL_DEPTH = 48).
  • Поток данных (цветные Data-пины): вычисляется лениво назад (evalInput → evalOutput) по запросу узла и кэшируется внутри одного прохода ExecScope.

Референсы объектов, иерархия и доступ к компонентам (v2.5)

  • Референсы через Exposed Variable + 3D-пипетку: создайте переменную типа entity с флагом Editable in Inspector и укажите целевой объект прямо на сцене 3D-пипеткой. Пустой вход entity автоматически ссылается на текущий объект (Get Self Entity).
  • Поиск объектов: Find Entity By Name, Find Entity By Tag и Find Entity By Component (возвращает первый объект и массив всех найденных entities).
  • Иерархия: Get Parent Entity, Get Child By Name (ищет среди прямых и вложенных дочерних сущностей) и Get Children (массив ID дочерних сущностей).
  • Универсальный доступ к компонентам: Has Component, Get Component Property и Set Component Property (чтение и изменение любых полей компонентов; также доступны в TS через api.findByName, api.findByComponent, api.getParent, api.getChildren, api.getChildByName, api.getComponent).

Система тегов (Entities, Prefabs, GameAPI и Event Graph v2.5.1)

Теги задаются в Inspector → Tags у любой сущности и в Prefab Editor → Tags у префабов (автоматически наследуются при спавне). В рантайме доступны api.findByTag(tag), api.hasTag(id, tag), api.addTag(id, tag), api.removeTag(id, tag) и api.getTags(id), а в Event Graph — обновлённый Find Entity By Tag (отдаёт First Entity и массив All Entities для For Each), Has Tag, Get Entity Tags, Add Tag и Remove Tag.

Event Graph Nativization (AOT-компиляция в нативный JS при экспорте v2.5.2)

В окне Project → Export settings доступна опция Compile Event Graphs to native JavaScript on export (settings.export.nativizeEventGraphs). Когда она включена, packages/exporter/src/nativizeEventGraph.ts при сборке под Web, Яндекс Игры, Poki и Desktop автоматически компилирует все графы eventGraph (включая префабы) в статические ES-модули без eval() (100% CSP-safe и нативная скорость JS). В режиме Play внутри редактора при этом остаётся мгновенный живой интерпретатор.

Рецепт 1. Звук шагов по материалу под ногами (террейн + любые 3D-модели)

ts
export default function (api: GameAPI) {
  let stepTimer = 0
  const footstepMap: Record<string, string> = {
    Asphalt: 'sfx-step-asphalt',
    Grass: 'sfx-step-grass',
    Mud: 'sfx-step-mud',
    Wood: 'sfx-step-wood',
  }
  return {
    onUpdate(dt: number) {
      const [mx, mz] = api.input.move
      if (!api.player.isGrounded || Math.hypot(mx, mz) < 0.15) return
      stepTimer -= dt * (api.player.isSprinting ? 1.55 : 1)
      if (stepTimer > 0) return
      stepTimer = 0.42

      // Работает и на террейне (учитывает слой кисти), и на любом 3D-меше
      const hit = api.materials.getSurfaceAt(api.player.position, [0, -1, 0], 2.0)
      const sfx = (hit && footstepMap[hit.materialName]) || 'sfx-step-default'
      api.audio.play(sfx, { bus: 'sfx', volume: 0.7, pitch: 0.92 + Math.random() * 0.16 })
    },
  }
}

Рецепт 2. ИИ-патруль NPC на NavAgent с нарезанными анимациями

ts
export default function (api: GameAPI) {
  const waypoints: [number, number, number][] = [
    [0, 0, 0], [12, 0, 4], [10, 0, -10], [-4, 0, -6],
  ]
  let idx = 0
  let wait = 0

  const goNext = () => {
    api.nav.moveAgent(api.entity.id, waypoints[idx], {
      speed: 2.4,
      stopDistance: 0.45,
      walkClip: 'Walk',   // клип, нарезанный в Model Editor
      idleClip: 'Idle',
      crossfade: 0.25,
    })
  }
  return {
    onStart() { goNext() },
    onUpdate(dt: number) {
      if (api.nav.isAgentMoving(api.entity.id)) return
      wait += dt
      if (wait >= 2.0) {
        wait = 0
        idx = (idx + 1) % waypoints.length
        goNext()
      }
    },
  }
}

Рецепт 3. Динамический цикл дня и ночи + фонарик + Sun Rays

ts
export default function (api: GameAPI) {
  let hour = 10 // 0..24
  let torchOn = false
  return {
    onUpdate(dt: number) {
      hour = (hour + dt * 0.15) % 24
      const angle = ((hour - 6) / 24) * Math.PI * 2
      const sunY = Math.sin(angle)
      const dayFactor = Math.max(0, sunY)

      api.environment.setSun([Math.cos(angle), Math.max(0.08, sunY), 0.35],
        dayFactor > 0.2 ? '#fff4de' : '#ff9f68', 0.25 + dayFactor * 1.45)
      api.environment.setAmbient(0.22 + dayFactor * 0.65)
      api.environment.setFog(dayFactor > 0.1 ? 0.012 : 0.028, dayFactor > 0.1 ? '#b7c7d6' : '#141c28')

      if (api.input.pressed('Flashlight')) {
        torchOn = !torchOn
        api.lights.setFlashlight({ enabled: torchOn, color: '#fff3d6', intensity: 3.2, range: 22, angle: 0.55 })
      }
    },
  }
}

Система плагинов (Plugin API v2.2): создание, импорт и разработка

Архитектура плагинов Miniforge Engine v3.0, формат .mfplugin.json, полный справочник EditorPluginContext и RuntimePluginContext, разбор 4 встроенных примеров от простого HUD до RPG-инвентаря.

Начиная с версии v2.2, в Miniforge Engine встроена полноценная модульная система плагинов. Плагины хранятся прямо в проекте как ассеты типа plugin, поддерживают экспорт/импорт в одном файле (.mfplugin.json или .js), умеют расширять как Редактор (добавлять команды в верхнее меню Plugins, модифицировать сцену и ассеты), так и Рантайм (регистрировать собственные Behavior-компоненты, глобальные сервисы, HUD-интерфейсы и хуки игрового цикла).

1. Где управлять плагинами и как их импортировать

  • Создание нового плагина: в верхнем меню нажмите Plugins → + New Plugin или в панели Assets → + New → Plugin. Откроется встроенный Plugin Manager с редактором метаданных, редактором кода, валидатором синтаксиса и кнопкой Save changes.
  • Импорт готовых плагинов: перетащите файл .mfplugin.json прямо на панель Assets (Drag & Drop) или нажмите Import .mfplugin.json / .js внутри Plugin Manager. Импортированный плагин автоматически включается и активирует свои пункты в меню Plugins.
  • Экспорт и распространение: кнопка Export .mfplugin.json выгружает самодостаточный JSON-манифест со всем кодом и метаданными — его можно передать другому разработчику или перенести в другой проект Miniforge.
  • Встроенная галерея примеров: во вкладке Example Plugins внутри Plugin Manager доступны 4 готовых плагина возрастающей сложности с установкой в один клик (Install).

2. Формат манифеста .mfplugin.json

Каждый плагин описывается структурой PluginManifest (определена в packages/project-schema/src/plugins.ts). Поле code содержит обычный JavaScript-модуль (CommonJS-стиль с объектом exports):

json
{
  "id": "my-custom-plugin",
  "name": "My Custom Plugin",
  "version": "1.0.0",
  "author": "Indie Dev",
  "description": "Краткое описание возможностей плагина",
  "category": "runtime",
  "enabled": true,
  "code": "exports.registerRuntime = function(ctx) { ... };"
}
ПолеТипОписание
idstringУникальный идентификатор плагина (slug), например fps-counter-hud.
namestringОтображаемое название плагина в списке ассетов и Plugin Manager.
versionstringВерсия плагина в формате SemVer (например, 1.0.0).
authorstringИмя автора или студии.
category"gameplay" | "editor" | "ui" | "world" | "utility" | "runtime"Категория для визуальной группировки в менеджере плагинов.
enabledbooleanФлаг активности. Отключённый плагин остаётся в проекте, но его хуки не запускаются ни в редакторе, ни в рантайме.
codestringИсходный JavaScript-код плагина с точками входа exports.registerEditor и/или exports.registerRuntime.

3. Точки входа и жизненный цикл плагина

Код плагина компилируется изолированно через new Function('exports', code) и может экспортировать одну или обе функции регистрации:

  • exports.registerEditor(ctx) — вызывается в редакторе при загрузке проекта, переключении флага enabled или сохранении кода плагина. Используется для регистрации пунктов меню Plugins и инструментов генерации контента на сцене.
  • exports.registerRuntime(ctx) — вызывается при старте игровой сессии (Play в редакторе или экспортированный билд) до инициализации сущностей сцены. Регистрирует кастомные Behavior-компоненты, сервисы и хуки игрового цикла.

7. Пошаговый пример разработки собственного плагина

Ниже показан минимальный гибридный плагин, который одновременно добавляет инструмент в редактор и регистрирует кастомный Behavior в рантайме:

js
exports.registerEditor = function(ctx) {
  ctx.registerMenuAction({
    id: 'spawn-beacon', label: 'Spawn Rotating Beacon',
    run: function() {
      ctx.patchScene(function(scene) {
        var entity = {
          id: ctx.uid('beacon'), name: 'Signal Beacon',
          transform: { position: [0, 1.5, 0], rotation: [0, 0, 0], scale: [0.6, 1.8, 0.6] },
          components: [
            { type: 'mesh', primitive: 'cylinder', color: '#f59e0b' },
            { type: 'behavior', kind: 'beaconSpinner', params: { speed: 2.2 } }
          ]
        };
        return Object.assign({}, scene, { entities: scene.entities.concat([entity]) });
      });
      ctx.notify('Signal Beacon добавлен на сцену');
    }
  });
};
exports.registerRuntime = function(ctx) {
  ctx.registerBehavior('beaconSpinner', function(api, params) {
    var speed = (params && params.speed) || 1.5;
    return { onUpdate: function(dt) { api.transform.rotation[1] += speed * dt; } };
  });
};

8. Рекомендации по разработке и отладке плагинов

  • Проверяйте синтаксис до запуска: кнопка Validate в Plugin Manager прогоняет компиляцию кода и сразу показывает строку ошибки без перезапуска сцены.
  • Всегда очищайте ресурсы в onDestroy: если плагин монтирует DOM-элементы через api.ui.mount() или вешает слушатели window.addEventListener, удаляйте их в ctx.onDestroy, чтобы не оставлять «призраков» после выхода из режима Play.
  • Общайтесь между плагинами через сервисы: вместо глобальных переменных на window регистрируйте API через ctx.registerService('mySys', apiObj, api) и получайте его из других плагинов или Event Graph через api.services.get('mySys').
  • Сохраняйте прогресс через api.worldState: данные, записанные в worldState (как в примере rpg-inventory-loot), автоматически переживают смену сцен и участвуют в системе сохранений движка.

3. Компонент NetworkSync и автоматические аватары

  • owner: "local" (Игроки): Каждый клиент управляет своей капсулой/персонажем, а рантайм сам создаёт цветной прокси-аватар для каждого подключившегося соперника и удаляет его при выходе (leave / onPeerLeave).
  • owner: "host" (Общие объекты): Враги, двери, платформы и лут симулируются только на Хосте и синхронизируются клиентам. Steam следует владельцу лобби. В остальных транспортах хост определяется по наименьшему peer ID в списке. Передача роли не восстанавливает состояние матча.
  • Transform, Анимации и дельта Sync Keys: Синхронизируются позиция/поворот/масштаб (интерполяция углов по кратчайшей дуге), animState + animClip кроссфейд, глобальный WorldState (vars) и произвольные поля сущности (hp, ammo, score) через api.net.setEntityVar(). Поздно вошедшие игроки автоматически получают актуальные значения при onPeerJoin.

Quick Tips (новые и базовые фичи)

  • Комнаты и лобби (LAN, WebSocket, Steam): Все режимы разделяют матчи по roomCode. В Desktop LAN вызывайте hostLan() на хосте и discoverLan(1400) на клиентах для автопоиска комнат (UDP-порт 41234). В Steam используйте createLobby() + setLobbyData() + listLobbies() с AppID 480 для бесплатных тестов.
  • owner: "local" vs owner: "host": На сущности игрока всегда ставьте owner: "local" — движок сам создаст цветной прокси-аватар для каждого соперника. На общих врагах, дверях, ящиках и переключателях ставьте owner: "host", чтобы их симулировал только Хост.
  • Синхронизация HP, счёта и параметров скриптов: Пропишите ключи в Sync Keys (например hp, score) и обновляйте их через api.net.setEntityVar(api.entity.id, "hp", hp). Отправляются только изменения (дельта), а поздно вошедшие игроки автоматически получают весь срез при onPeerJoin.
  • Vector3 Transform API в скриптах: api.transform.position и api.transform.rotation — это объекты Vector3: всегда меняйте их через .set(x, y, z) или .x/.y/.z (никогда не присваивайте массив [x, y, z]!). Глобальные переменные матча храните в api.vars, а имена биндингов пишите с учётом регистра (api.input.pressed("Jump"), "Interact").
  • Dual Preview и Split-Screen: В Multiplayer Studio → Launch Host + Client кликните внутрь окна HOST или CLIENT, чтобы передать фокус клавиатуры. Для локального коопа используйте api.net.getLocalPlayerMove(0..3) (P1: WASD, P2: Стрелки, P3: IJKL, P4: Numpad + геймпады 0–3).
  • GLSL-шейдеры и Scatter Brush: В Shader Studio пишите void mainImage(out vec4 color, vec2 uv) и/или void mainVertex(inout vec3 position, inout vec3 normal) (не пишите void main()). Держите staticBatch включённым на пропах из Scatter Brush и проверяйте draw calls во вкладке Performance.
  • Экспорт и пересборка рантайма: Включайте AOT Nativization для Event Graph в Export Settings. После правок исходников движка локально запускайте pnpm prepare:runtime (или pnpm dev), чтобы пересобрать apps/editor/public/engine/web.js.

Рецепт 2: Создание и поиск Steam-лобби (AppID 480)

steamMatchmaking.ts
export default function createBehavior(api) {
  return {
    async onStart() {
      const user = await api.steam.init()
      if (!user.steamId) throw new Error("Steam unavailable")
      const lobbies = await api.steam.listLobbies()
      const match = lobbies.find(lobby => lobby.data?.game === "miniforge-arena")
      const lobby = match
        ? await api.steam.joinLobby(match.id)
        : await api.steam.createLobby({
            name: "Arena Match", maxMembers: 4,
            data: { game: "miniforge-arena", map: "arena_01" },
          })
      if (!lobby) throw new Error("Could not join lobby")
      const connected = await api.net.connect({ mode: "steam-p2p", room: lobby.id })
      if (!connected) {
        await api.steam.leaveLobby()
        throw new Error(api.net.getLastError())
      }
      await api.steam.setRichPresence("status", "В бою на арене")
    },
  }
}

Первое окно инвентаря

  1. Откройте Project → UI editor и создайте экран типа Window. Скопируйте ID экрана. В примере ниже это bag.
  2. Добавьте Counter и Progress. Скопируйте ID элементов. Для примера подставьте их вместо coins и healthBar. Укажите текст счётчика «Монеты».
  3. Добавьте объект со Script в сцену. Вставьте скрипт и запустите Play. Окно должно открыться со счётчиком 12 и заполненной на три четверти полосой.
export default function (api: GameAPI) {
  return {
    onStart() {
      const ui = api.ui
      ui.setPosition('healthBar', 8, 12)
      ui.setSize('healthBar', 40, 4)
      ui.setProgressMax('healthBar', 100)
      ui.setValue('healthBar', 75)
      ui.setOpacity('healthBar', 0.9)
      ui.setColors('coins', '#ffffff', '#28303b')
      api.vars.gold = 12
      ui.bindValue('coins', 'gold')
      ui.open('bag')
    },
  }
}

Меняйте api.vars.gold во время игры, чтобы счётчик следовал за переменной. setValue устанавливает явное значение. Повторный bindValue возвращает привязку. Для закрытого экрана значения сохраняются до следующего открытия в текущей игре. hasWidget(id) проверяет наличие элемента в модели HUD даже при закрытом окне. get(id) даёт доступ к текущему DOM-элементу. После перерисовки окна запрашивайте его заново. getValue(id) читает число и возвращает undefined при отсутствии числового значения.

Тот же HUD в Event Graph

  1. Поместите Event Start и соедините линию исполнения с Set UI Progress Maximum, затем с Set UI Value. Укажите ID полосы и числа 100 и 75.
  2. Добавьте Bind UI Value, выберите ID счётчика и задайте имя переменной gold. Выполните Open UI Screen с ID окна.
  3. Для необязательного элемента соедините выход UI Widget Exists с условием Branch. Get UI Value выдаёт число, а при отсутствии значения выдаёт 0. Для выбора другого цвета по событию используйте Set UI Colors.
  4. Проверьте сцену в Play, затем экспортируйте Web с включённой компиляцией Event Graph. В обоих случаях проверьте значение после закрытия и повторного открытия окна.

Quick tips

  • X и Y измеряются в процентах от области размещения, относительно выбранного якоря. Раскладкой детей контейнера управляет сетка или список.
  • Для живых числовых показателей используйте привязку. Цвет текста и фон меняются через setColors. Оформление отдельных DOM-свойств через setStyle действует на текущий экземпляр элемента.
  • Для HTML-виджета с собственным скриптом используйте события его iframe. Метод setHtml и нода Set UI HTML заменяют содержимое кадра, сохраняя CSS и JS привязанного ассета. Для обычного HUD достаточно стабильного ID элемента.
  • В профайлере откройте Play для измерения фактических draw calls. Для игры с GI проверьте отдельно время открытия сцены и время кадра после расчёта.
  • Для локальной сетевой проверки используйте два клиента. Для интернет-проверки откройте их в разных сетях. Steam Relay Lab запускается в Local Debug через обычный Play или с нативным Steamworks через Play with Steam в Desktop-редакторе. Проверка Steamworks

Метка над объектом в 3D-сцене

Создайте виджет верхнего уровня с якорем Top Left. Его координаты будут отсчитываться от верхнего левого угла так же, как результат проекции.

const point = api.camera.worldToScreen(worldPosition)
api.ui.setVisible('targetMarker', point.visible)
if (point.visible) api.ui.setPosition('targetMarker', point.xPercent, point.yPercent)

В Event Graph соедините World To Screen 2D → Visible с Set UI Visible, а Screen X (%) и Screen Y (%) с координатами Set UI Position. Добавьте условие Branch, чтобы обновлять позицию только у видимой метки. Пиксельные выходы по-прежнему доступны. Проекция учитывает ортографическую камеру, поворот камеры и размер области игры. За пределами кадра проценты могут выходить за диапазон 0–100. Visible означает попадание в кадр. Перекрытие объектами сцены на него не влияет.

Вызовы Set UI Visible и Update UI Widget подходят для Event Update. Изменение видимости отдельного элемента сохраняет DOM соседних виджетов, включая кнопки диалога. Get Active UI Screen возвращает ID открытого окна или текущего HUD. Is UI Widget Visible проверяет видимость виджета с учётом экрана и скрытых контейнеров. Для проверки самого ID, в том числе на закрытом экране, используйте UI Widget Exists.

Advanced lighting, local reflections & surface decals (experimental)

Advanced lighting, local reflections & surface decals (experimental)

This change extends the 3.0.3 Render Optimization + TypeScript Fix build. It retains the LittleJS 1.30.1 renderer and injects changes through packages/graphics/multi-shadow.js when device.mjs creates the renderer.

Lighting and dynamic shadows

  • Directional light (sun): original shadow map.
  • Spotlight: up to 4 separate maps with automatic selection, maintained from the previous Adaptive Shadows change.
  • Point Light: new six-face 3×2 depth atlas per selected light, supporting 0–2 active point-light shadow casters. A point light shadows in all directions.
  • Set Cast Shadow on a Point Light in its inspector. The engine automatically chooses lights using viewport intersection, distance, intensity and range. Shadow priority and Pin shadow slot are optional overrides.
  • Scene lighting Max point-light shadows controls the GPU budget (default 1). Point lights use 6 depth passes each, in addition to the sun and spot passes.
  • Point shadow resolution: low 128 px/face, medium 256, high 512.
  • LittleJS still shades at most 8 dynamic lights at once (including selected shadow lights). All local light sources can contribute to static GI bakes, but 8 remains the direct-light limit for a rendered frame.
  • Ambient/Skylight does not have a direction and therefore does not cast a standard directional shadow. Static skylight occlusion remains part of GI.

Local reflection zones

  • Bake Zones now carry a box for parallax-corrected cubemap lookup. Both baked and realtime cubemaps use the same local correction.
  • Smaller overlapping enabled zones win over larger zones. Outside the zone, the global environment cubemap is used.
  • Zones follow their transform and parents. Capture height offset moves the cubemap capture point up or down without moving the zone bounds.
  • Reflection cubemap sizes include 512 for sharper reflections; it costs substantially more memory and 6 faces to capture each update.
  • The Water surface has Reflection strength and Reflection sharpness. It now participates in environment reflections, including nearby zone probes.
  • Limitation: a parallax-corrected cubemap is an approximation, NOT a true mirror-plane render. A close-up puddle at grazing angles may still have incorrect occlusion, displaced nearby objects and missing moving reflections between realtime refreshes. A separate planar reflection/SSR pass is needed for physically faithful mirror puddles.

Geometry-conforming decals

  • Select a Decal and use Projection: surface to clip neighboring static triangle meshes to the oriented decal volume. A generated patch receives the original decal UVs and texture; it follows slopes and uneven surfaces.
  • Projection depth controls the thickness of the projection box and limits bleed-through. Minimum surface facing rejects near-perpendicular walls.
  • Existing Projection: plane remains as a lightweight alternative.
  • The projector must face the target; rotate the decal to match the wall or floor, and set its depth to cover the relief.
  • Projection is capped at 12,000 generated triangles per decal. Reprojection happens after model loading and when the decal moves in the editor (throttled).
  • Limitations: projection is for static triangle geometry. Moving/skinned targets, overlapping UV atlases and extremely large triangle meshes are not a substitute for GPU deferred decals or a terrain decal material pass. Dynamic spawnDecal still uses the inexpensive flat quad.

Recommended verification

  1. Run pnpm test, pnpm typecheck, pnpm build.
  2. Sun + two Spotlights + a shadowed Point Light: verify 3 independent shadows.
  3. Move camera among 3 point lights with budget 1: selected point changes without affecting sunlight. Repeat with shadows disabled and Receive Shadow off.
  4. Place a Water plane inside a small Bake Zone. Position the cubemap near the water using capture height offset. Compare baked vs realtime mode as moving objects enter the view. Compare 128/512 px.
  5. Project a textured decal onto uneven terrain and a stair model; vary depth, angle and offset. Ensure no projection on a mesh outside its box.
  6. Export the game and repeat tests in the autonomous runtime.

Verification status in the prepared artifact: JavaScript syntax, TypeScript transpile syntax, and isolated geometry/selection tests have been checked. Surface Decals: screen-space projection (3.0.4 fix)

Surface Decals: screen-space projection (3.0.4 fix)

Surface Projection now uses a GPU full-screen depth reconstruction pass instead of generating clipped triangles. A decal is defined by an oriented volume and an optional Material/Texture asset. The pass runs after the LittleJS render and before Miniforge postprocessing; it reconstructs the visible world position from the depth texture, tests the position against the decal volume and samples the material base texture using projector-local UVs. The old Plane mode stays available.

Behavior: no decal geometry is generated; circular models and slopes no longer display seams from triangle clipping or normal offsets. The projected material supports base color/texture, alpha transparency, UV tiling/offset, emissive texture/tint and alpha/additive blending. On opaque models the projection follows the visible surface, even when its geometry moves and participates in the depth pass.

Limitations: this is a forward colour-overlay decal pass, not a deferred G-buffer decal. It does not override the receiving surface's roughness/metalness or apply a normal map to the underlying lighting. Surfaces that do not contribute to opaque depth (e.g. transparency with depthWrite=false) cannot receive screen-space projection. Because the pass runs after transparent rendering, its order against foreground transparent objects is not guaranteed. Cost scales with viewport resolution and number of projectors. No GPU-level integration test could run in this environment.

Why the black square may remain: alpha-blended projections respect the supplied PNG's alpha. If every pixel is opaque, the entire projected footprint remains visible. Use a transparent PNG or material alpha, or enable Dark background transparent with a suitable threshold for art with a black background. The dark-key option is intentionally off by default: legitimate black artwork must remain possible.

Check in editor: select the decal, choose Surface Projection (GPU / depth), place the projection volume so it intersects an opaque mesh (for a box 1–2 units large start with depth 2), and test with a transparent PNG. Rotate or animate the receiver to verify projection follows its visible surface. Compare against Plane mode, which should retain a flat quad.

Before publishing, run pnpm typecheck, pnpm test, pnpm build, pnpm export:demo, and visually verify shader compilation in WebGL2. The new render path relies on LittleJS's cameraDepthTexture and viewProjection fields.

Decal Surface Projection and Materials

Decal Surface Projection and Materials

Inspector

Select an entity with the 3D Decal component. The Projection mode selector offers:

  • Surface Projection (follow geometry) (default for new decals): the projector clips triangles of static Mesh, GLB and Terrain receivers and creates an overlay mesh that follows their relief. Set Projection depth to cover the target surface, and Minimum surface facing to exclude glancing surfaces. The projection is along the decal's local Z axis; adjust rotation to aim at the target.
  • Plane (flat quad): inexpensive flat decal, without geometry projection. This also remains the behavior of the runtime spawnDecal API.

Projection does not modify the underlying surface's geometry or material and does not support skinned/animated receivers.

Materials

Choose an existing Material asset, or click Create decal material. Decals use the same LittleJS-backed material options as Mesh renderers: base color/map, normal map, emissive map and tint, roughness-to-shininess mapping, reflectivity/metalness, custom shader, tiling and offset.

The Texture override field is optional. If set, it replaces the material's base color texture only; normal and emissive textures still come from the material. The Tint color multiplies the material's base color. The Opacity multiplies the material's opacity.

For correct overlay behavior decals always remain blended, depth-tested, depth-write-disabled, and do not cast shadows, irrespective of the chosen material's depth and casting defaults. They can receive shadows unless disabled by their material. Alpha vs additive is selected on the decal itself.

This is a geometry-backed forward-rendered overlay, not a deferred DBuffer decal. The decal's own normal/roughness/reflectivity affects how its generated overlay is shaded, but it does not directly rewrite the underlying surface's G-buffer attributes. Materials on decals cannot currently make a true per-pixel roughness-only modification to the underlying material without rendering an overlay.

Test procedure

  1. Add a static Box or Terrain and place a 3D Decal so that its volume intersects the surface.
  2. Choose Surface Projection, use adequate Projection depth and rotate the projector until it faces the target.
  3. Select an existing material with a base texture and a normal/emissive map. Verify lighting and UV tiling.
  4. Toggle to Plane and verify the decal becomes flat.
  5. Clear the material and set a texture directly: older texture-only decals should still render.
  6. Export the game and check that the decal's material and its textures are included.

Surface Decals — receiver and offset fix

Surface Decals — receiver and offset fix

This patch fixes three problems that prevented projected decals from appearing on nearby 3D meshes:

  1. The projection receiver filter incorrectly treated any entity with Behavior, Script, or EventGraph as dynamic. These components alone do not imply that a mesh is moving. Static mesh receivers with these components are now eligible. Animated, nav-agent and dynamic/kinematic physics geometry remains excluded.
  2. The generated geometry previously used a fixed local +Z normal offset. This can push the decal inside the model, depending on projector rotation. The projection now receives the mesh's outward normals, transformed with the inverse-transpose normal matrix for nonuniform scales, and offsets along the real surface normal.
  3. Alpha-blended mesh materials are no longer automatically excluded as receivers. Additive effects remain excluded.

Placing a decal on a model

Surface Projection is an oriented 3D volume, not a ray cast that searches the entire scene. Width and height cover its local XY rectangle. Projection Depth is the total depth, with half in each direction from the decal's transform origin. The projector must overlap the target mesh.

For example, in the FPS Explorer demo, Energy Beacon is centered at Y = 0.8 with a Y scale of 0.75. With the decal at approximately Y = 0 and depth = 0.8, the vertical extent of its volume is only approximately [-0.4, 0.4]. It does not quite reach the beacon's lowest point (approximately Y = 0.425). Move the decal toward the beacon, and/or increase depth to cover it. The supplied screenshot also places the decal about 0.54 units to the left of the beacon, so increasing width may help.

Surface projection onto a flat floor still looks flat, correctly; try covering the edge of a crate, pillar or beacon to confirm actual conformity. Minimum Surface Facing restricts projection onto nearly perpendicular faces; lower it for curved surfaces. Use Normal Offset to avoid z-fighting, not to extend the volume.

Limitations

This is triangle-clipped mesh decal projection, not a deferred/G-buffer decal. It does not deform onto a skeletal animated mesh, project through occluders using a depth buffer, or update skinned geometry each frame. Dynamic physics bodies and animated geometry remain intentionally excluded.

Checks

The projected-decal.test.ts suite now covers receivers with behavior/scripts, dynamic exclusions, orientation-independent normal offsets, slopes, clipping, and transforms.

CPU diffuse GI precomputation (3.0.x patch)

CPU diffuse GI precomputation (3.0.x patch)

What changed

graphics.bakeLighting(zoneId?) now runs an asynchronous CPU diffuse GI calculation rather than assigning one distance-based emissive color to every object.

  • Reads world-space triangles from LittleJS primitive and glTF meshes, including packed vertexData meshes.
  • Builds a triangle BVH and tests visibility before using light from directional, point and spot sources.
  • Traces cosine-weighted diffuse rays for bounced light and color bleeding from albedo; up to 3 diffuse bounces.
  • Samples emissive maps and base-color maps (including CPU-readable embedded glTF TextureInfo.image) at hit UV coordinates. Emissive geometry and emissive textures can therefore illuminate nearby static surfaces.
  • Produces diffuse-light textures per static mesh/part in the existing UV channel and composes them with the original emissive-map contribution. The original LittleJS obj.emissive intensity is not changed: doing so would turn off realtime lighting.
  • Direct light is not baked into the output; LittleJS already draws direct light and shadows. Baking the same direct light again would make scenes overly bright. Indirect light is baked as an additive emissive-map contribution.
  • Honors Bake Zone bounds and lightBounce strength. Reflection probes are refreshed after baking.
  • Uses generation/revision guards to cancel stale jobs when scenes change.

Settings

In Environment > Global Light Baking & Reflections, enable Bake static lighting and optionally tune:

GI lightmap resolution 24 px Per-mesh UV-space output size (8–64 allowed by runtime)
GI hemisphere samples 8 Diffuse rays per populated texel (2–64)
Diffuse bounces 2 Maximum diffuse path depth (1–3)

Higher values can slow startup considerably in complex scenes. await api.graphics.bakeLighting() triggers another bake from the current static scene state. api.graphics.bakeLighting(zoneId) limits receivers to the named Bake Zone.

Current limitations (important)

  1. Runtime precomputation, not exported/offline lightmaps. This patch recalculates GI when loading a scene with baking enabled. It does not serialize baked texture pixels into the project ZIP. For large games, an editor-side offline bake/export pipeline should be added next.
  2. Only LittleJS's original UV channel is available. Overlapping / tiled UV islands share output texels, so per-face shadow detail can blend together. Proper atlas unwrap with a separate UV2 channel requires a renderer/shader change; avoid assuming that this patch delivers production-grade lightmaps on arbitrary models.
  3. Imported glTF emissive maps are sampled when TextureInfo.image is CPU-readable. If a source image cannot be read (e.g. cross-origin), that material's original GPU emission is preserved and no replacement map is installed on it.
  4. Transparent objects, custom shaders, animated and dynamic objects are not baked as static geometry. Dynamic lights still affect direct lighting, but their indirect contributions are frozen until a new bake.
  5. The diffuse Monte Carlo solution is approximate: finite low-resolution samples, simplified Lambertian BRDF, approximate ambient sky and no mirror/specular GI. This is not an unbiased production path tracer or a volumetric light-field solver.
  6. UV outputs are LDR (8-bit), so very bright HDR emissive colors can clip. Keep source emission calibrated.
  7. Batching is disabled on scenes where GI baking is active, because the current single-UV-channel static mesh merger would discard each object's individual lightmap. Restoring efficient batches needs lightmap atlas packing/instancing-aware material keys.

Validation

  • Fast CPU tests: node --experimental-strip-types --test tests/baked-gi.node.test.mjs (Node 22+).
  • Regular build/typecheck (requires installed project dependencies): pnpm typecheck && pnpm test && pnpm build.
  • Manually validate scenes with separate red/blue emissive map patches, a thin occluding wall, enclosed corners and light-emitting mesh parts. Compare direct light with baking enabled/disabled to ensure it is not doubled.

GPU Projected Decals: materials, culling, and batching

GPU Projected Decals: materials, culling, and batching

This update extends the working Surface Projection (GPU / depth) mode. It does not revert to triangle-clipped overlay geometry. The simple Plane mode is unchanged.

Features

  • Material overlays: use the Material Asset's base texture/color, normal map and normal scale, roughness and metalness, emissive texture/color and intensity, UV transform, opacity and alpha cutoff. An optional separate decal texture overrides only the base map. Material Assets also expose optional roughnessMap and metalnessMap (single-channel red-channel maps).
  • Forward lighting: reconstructs the receiver's world normal from the depth texture, applies the normal map, and lights the decal using the scene's sun, ambient and up to 8 selected dynamic LittleJS lights. The metallic and roughness parameters participate in its specular BRDF.
  • Projector culling: rejects decal volumes completely outside the clip frustum. For projectors inside/intersecting it, computes a conservative projected bounding rectangle; the GPU only shades that rectangle, not the entire screen. Near-plane intersections use a safe full-screen fallback.
  • GPU batching: consecutive decals sharing base, normal, roughness, metalness, and emissive textures and blending state are submitted with gl.drawArraysInstanced, up to 64 per draw. Per-projector matrices, bounds, UV transforms, tint and material values stay independent. No sorting is done, so overlaps keep their original alpha compositing order.
  • Auto-enabled: culling and batching need no extra scene flags. Empty and invisible decal sets skip the GPU pass entirely.

Known limitations

The engine is a forward renderer. Unlike a deferred decal that writes a material G-buffer, this implementation shades a separate decal overlay on top of the rendered image. It cannot change the receiver's underlying BRDF or receive all shadows, GI, SSR, or scene reflection probes identically to the receiver. Custom Material Asset shader snippets are not executed by the GPU decal overlay. The optional roughness/metalness texture maps currently apply only to GPU decals, not ordinary mesh materials.

Full decal G-buffer modification requires extending the scene render pipeline with normal/material render targets and a proper material-composition pass. Do not represent this forward approximation as equivalent to deferred PBR decals.

Performance

Instance batches keep the scene's decal order. If hundreds of footprints have identical textures and consecutive z-order, they use fewer draw calls, but transparent overdraw still costs GPU time. Mixed texture groups cannot all be combined into a single call without atlasing or texture-array packaging.

Regression checklist

  1. pnpm typecheck, pnpm test, pnpm build.
  2. In FPS Explorer place a Surface Decal on a round mesh, add a normal-map material and verify relief lighting without polygon seams.
  3. Change roughness and metalness; specular response should change while the receiving mesh and its base material remain unmodified.
  4. Use an emissive map and verify alpha/dark-key backgrounds.
  5. Place 100 copies of the same decal; inspect draw calls. Move them outside the viewport and verify the count drops.
  6. Overlap transparent and additive decals with different textures; layer order should remain stable.
  7. Export the scene and compare the standalone result with the editor.

A GPU visual test was not available in the automated environment; treat shader compilation and frame-level blending as needing an in-browser test.

Miniforge: multiple real-time shadow sources

Miniforge: multiple real-time shadow sources

What changed

The LittleJS 1.30.1 renderer normally has one shadowLight: choosing a spotlight replaces the sun's shadow pass. Miniforge now compiles packages/graphics/multi-shadow.js into the same lexical scope as the pinned LittleJS release via packages/graphics/device.mjs. It retains the existing solar shadow map and generates up to four additional shadow maps for spotlights. Each light contribution is attenuated by its own depth map in the existing physically approximate LittleJS lighting shader. The sun's shadows do not darken the contribution of another spotlight.

No installed dependency or node_modules contents are modified. Custom LittleJS shaders that use the standard lighting pipeline receive the same per-light shadows.

How to use in the editor

  1. Enable Shadows under scene/environment settings.
  2. Choose global Shadow quality. This controls the sun's map and is inherited by spotlights by default.
  3. Set Dynamic spotlight shadows to 1–4 (default 4).
  4. On each Spotlight enable Cast shadow (active). The renderer automatically chooses the most significant on-screen spotlight casters each frame. Pin shadow slot is optional and forces a light to occupy one of the available slots; Shadow priority adjustment only biases automatic ranking. Optionally override Shadow resolution.
  5. Press Play, preview, or export the game. The sun and enabled spotlights should now each cast independent shadows.

The scripting method setShadowLight(id) pins a spot caster rather than replacing the sun. Calling setShadowLight(null) clears dynamic spotlight casters (but keeps sun shadows). Setting a spotlight gobo/gel through setLightGel also enables its projection.

Performance / limits

  • Up to one solar directional shadow plus four spotlight shadow maps. Point lights still illuminate dynamically, but do not cast real-time omnidirectional shadows (use GI bake for static indirect/occluded light); a correct omnidirectional solution requires a cube depth texture or six passes per point light.
  • Every additional spotlight depth map requires an additional geometry draw from that light's viewpoint. Reducing the shadow cap, using 512px maps for secondary lights, and choosing smaller light ranges improves performance.
  • WebGL2 uses texture units 1 (sun), 6–9 (spot depth), and 10–13 (spot gel textures). The design fits the WebGL2 minimum fragment texture unit count of 16.
  • Four spots are selected from active, eligible spotlights using conservative cone/frustum intersection, estimated screen coverage, proximity, brightness and an optional priority adjustment. Previously selected sources have a 30% score advantage to reduce frame-to-frame flicker. Pinned sources take precedence even when off-screen; pin no more than the configured slot limit. When the eight-light LittleJS cap is reached, selected spots replace lower-priority ordinary lights rather than displacing one another.
  • Receive Shadow on a material and the scene's global Shadows switch continue to gate shadowing. Depth maps use LittleJS's existing castShadow mesh flags.
  • This is a renderer extension coupled to LittleJS 1.30.1 internals. It must be revalidated on every LittleJS update, especially the render3DFragmentSource shader anchors and shadow pass implementation.

Validation

Run:

pnpm install
pnpm test
pnpm typecheck
pnpm build

Test with at least 9 local lights and move the camera between groups of spotlights; verify selection changes without flicker. Test pinned lights separately. Inspect WebGL error logs on a real GPU. Node-only unit tests cannot verify WebGL shader compilation or framebuffer completeness.

Implementation locations

  • packages/graphics/multi-shadow.js: GLSL lighting extension, four persistent shadow-map resources, per-source uniforms, GL cleanup.
  • packages/graphics/device.mjs: inject the extension in the generated device alongside LittleJS.
  • packages/graphics/src/index.ts: collect spot casters and priorities per scene, preserve them through playback, handle scripting API.
  • apps/editor/src/Authoring.tsx, apps/editor/src/Inspector.tsx: quality and priority controls.
  • tests/multi-shadow.test.mjs: source injection and selection rules.

Miniforge 3.0.4 — Networking and Steam audit

Historical audit

This document records the relay hardening that preceded native Steamworks. The Rust Steamworks bridge now ships in the Desktop editor and Steam-enabled depot exports. See Steamworks setup and the current network roadmap.

Summary

The initial audit hardened the existing relays and made the Local Debug simulation explicit. The notes below describe the routing and preview contracts that are still relevant.

Networking: repaired

  • Node WebSocket relay now binds to 127.0.0.1 by default, unless explicitly passed a public bind address. Each connected socket owns an immutable peer ID and room. A forged from, a room switch or a duplicate peer ID is rejected.
  • Native Tauri LAN WebSocket relay uses the same join-first, immutable peer/room and authoritative peer-list semantics. The old code forwarded every message to every LAN client, ignoring rooms.
  • Relays reject oversized packets (256 KiB), unmasked text frames and unsupported frame fragmentation. The Node server additionally validates the handshake, limits packet rate and supports optional shared access token on join.
  • The Node status endpoint no longer lists arbitrary room names. Remote deployments should use wss:// behind a TLS reverse proxy and configure authentication appropriate for the game. A shared token embedded in a publicly downloaded web game is not a secure secret or proof of player identity.
  • A WS upgrade no longer counts as a connected player. NetManager.connect() now returns true only after the server sends a peer-list acknowledging that the player was admitted to the room.
  • No more silent fallback from failed remote WebSocket to BroadcastChannel. url: 'local' remains explicit, for editor previews / multiple tabs only. hostLan() in a browser now returns null rather than pretending to host a LAN server.
  • Remote WebSocket reconnection preserves peer ID, room, and token; reconnect timers and DataChannels are cleaned up; peer join/leave notifications are refreshed.
  • WebRTC uses one reliable ordered DataChannel. Messages to recipients with an open DataChannel are not redundantly sent over WebSocket; recipients still connecting use the signaling relay. ICE candidates arriving before remote SDP are queued.
  • Sender identity on DataChannel and Steam P2P packets is taken from the transport, not from the untrusted packet body.
  • Game runtime rejects invalid/NaN position and rotation snapshots and enforces host ownership of host-owned snapshots and global state. Remote dynamic entity property names are constrained.
  • Packet room, chat sender, RPC name and pong RTT values are checked. The relay is not a server-authoritative anti-cheat layer; game rule validation remains a responsibility of the game/server.

Steam and verification

  • Local Debug remains an editor simulation. In a Desktop editor built with Steamworks, Play with Steam opens a native session using the installed SDK. Native initialization errors surface in the editor.
  • Exported Steam games use the native bridge when Steam initialization succeeds. Browser exports require another transport for online play.
  • pnpm test:network covers real WebSocket and BroadcastChannel sessions, routing rules and the sandboxed preview simulation. Native IPC mocks and archive checks cover the build and launch contracts. Check Steam accounts, remote networks and LAN discovery in separate acceptance runs.

Follow-up: working network example previews

See NETWORK_EXAMPLES_3_0_4.md. Local Steam Debug across isolated editor preview iframes is now explicitly bridged by the parent editor via a same-origin BroadcastChannel. Exported builds do not use this bridge. When localStorage is blocked in an opaque-origin iframe, debug cloud and achievement data use volatile memory; this is not real Steam Cloud or persistent storage.

Render optimization pass (Miniforge 3.0.3)

Render optimization pass (Miniforge 3.0.3)

P0: static batching safety

Batchable primitive and model objects are kept alive, with the original mesh, renderer, scene node and pick data intact. Only their render pass is suppressed while the derived merged/instanced object exists. Editing color, material, emission, shader or visibility releases the affected entity back to individual rendering; all other entities retain their batch. SceneNode world transforms (including parent changes) are checked in sync() and trigger release on change. playAnimation() and live textures also release instances.

P0: Scene Profiler

When Preview runs, the profiler uses actual runtime FPS, frame time and draw-call counts sent by runtime; draw calls include shadow passes. Without Preview, the profiler explicitly displays an estimate that accounts for spatial batching and repeat GLB candidates. Estimated draws treat each GLB as a single mesh; actual files can contain multiple submeshes. Triangle telemetry excludes hidden original meshes and includes instanced copies.

P1: GLB GPU instancing

Repeated compatible non-animated, opaque GLBs sharing the same model asset and material overrides inside a spatial cell can be placed in LittleJS InstancedMesh3D buffers, once for each GLB part. Matrices are taken from the full GLTF world transform. Animated and skinned GLBs, models with custom shaders, transparent parts and individually distance-culled models are excluded. Runtime changes release an instance back to its original GLTFObject. The staticBatching performance switch gates the feature. Per-model properties.instancing=false opts out; the primitive-specific staticBatch flag does not disable GLB instancing (auto-static-batching marks all models staticBatch=false).

P1: spatial mesh batching

Static mesh parts are grouped in world-space 16-unit cells with no more than 128 entities per draw. Each chunk is positioned near its own geometry rather than the world origin so LittleJS frustum culling operates with reasonable bounds. Mesh normals use inverse-transpose transforms and negative determinants reverse triangle winding. Any enabled per-entity distance culling disables spatial batching rather than breaking individual visibility.

P1: same-context post processing

Post-FX now takes the existing WebGL2 context from the device. Immediately after the 3D frame is drawn, a GPU framebuffer copy (gl.copyTexSubImage2D) creates a source snapshot and a fullscreen triangle composites the result to the original canvas. There is no second canvas, context or CPU canvas re-upload. This is still an extra full-frame GPU copy; an FBO-based render graph can remove that copy in a later change.

P2: multi-material batching

Compatible opaque materials may differ by base color and diffuse texture, which are baked into vertex colors and a padded per-chunk diffuse atlas. Remaining material parameters (roughness, metallic response, normal maps, emissive maps, shaders, alpha testing, depth/blend state) must match for one draw. Materials with normal/emissive maps, custom shaders, tiling/offset, transparency or special blending currently retain individual draws. This is a real multi-diffuse-material draw, not arbitrary physically based multi-material merging.

Validation and compatibility

  1. pnpm test and pnpm typecheck.
  2. Preview/export with settings.performance.staticBatching=true; inspect console and actual draw calls with/without batching.
  3. Test 200 static cubes in nearby and distant chunks, materials with solid colors and diffuse textures.
  4. Test two static GLBs with different transforms. Confirm originals can still be picked and runtime animation/movement restores normal draw behavior.
  5. Test active/parent visibility, mutations, negative scales, cull distance, shadow casting and GI Baking.
  6. Turn on bloom/DOF while moving camera, verify one WebGL2 context and absence of WebGL errors.

Limitations: GI Lighting intentionally disables static merging and GLB instancing to preserve per-object baked maps. The profiler's fallback estimate is approximate. This change was prepared without npm dependencies or a GPU test environment, so browser/WebGL and full project CI checks remain necessary.

Network Sync — selected fields and entity lifecycle (3.0.4)

Network Sync — selected fields and entity lifecycle (3.0.4)

Inspector

  • Owner authority: Host (shared world objects) or Local player owned (independent proxies per peer).
  • Sync Transform: position/rotation/scale. Sync Animation: current state/clip.
  • Sync Active / Visibility: shares Entity.active using host/owner snapshots; children follow normal entity hierarchy.
  • Sync Spawn / Despawn: host-owned prefabs created by api.net.spawnNetworkPlayer use stable root IDs and new peers receive their spawn records. api.destroy of host-owned synced entities is propagated and stored as a tombstone for late joiners.
  • Sync Paths: comma-separated selected paths. properties.hp, properties.inventory.gold, components.light.intensity, components.mesh.color, components.behavior.params.speed, components.light[1].range.
  • Sync Keys is retained as an old-project alias for properties.*.
  • A helper dropdown in Inspector can add existing entity properties and simple component fields. Up to 32 valid selected paths are sent per entity per tick. Paths are explicitly allowlisted on the receiving side.

Script API

api.net.setSyncedField('door-1', 'properties.open', true)
const isOpen = api.net.getSyncedField('door-1', 'properties.open')

The field must be selected in the entity's Network Sync Inspector. The default host authority blocks client writes to shared world objects when connected. Only plain bounded JSON values are supported. Executable script code, component types/IDs/assets, prototypes and network sync internals cannot be remote-written.

Component data is replicated as configuration. Supported live-render updates include light intensity/color/range, mesh color/material, decal opacity and particle rate. Other component fields are updated in the scene object, but may require an additional behavior listener via net.fieldChanged to apply live. A complete generic PBR renderer patch for all component fields is not part of this change.

Collectibles in Multiplayer Arena

The Energy Beacon now has host-owned Network Sync with Sync Active enabled. A client approaching the beacon sends a pickup request. The host validates the requesting peer's network player proxy and distance before hiding the beacon. Other players receive active: false through the normal snapshot. Score is awarded to the collecting client. Late joiners receive the host's current active state on the next snapshot.

Limitations

  • Current packets are tick-based snapshots, not a transactional replicated database. Path changes can be missed if rapidly changed and reversed within the same network tick.
  • Reconnects and late joins cause a full snapshot of selected fields; spawned entities and destroyed tombstones are also sent by the host (bounded to 256 spawns, 512 tombstones per join).
  • net:spawn only accepts a prefab already in the project and a host-supplied root ID. Only the host may spawn shared prefabs; peer-owned player proxies remain separate.
  • No protocol version migration or server persistence. The transport can elect a new host or follow the new Steam lobby owner. Recovery of the previous host’s match state is not implemented. Network roadmap
  • The WebSocket relay authenticates connection identity, not game actions. Critical actions must be checked by the host, as pickup is in this example.
  • Collection range uses the peer's last transmitted position, with a 0.3-unit tolerance to allow for network delay.

Графика Miniforge на LittleJS

Графика Miniforge на LittleJS

Редактор сцены, миниатюры, игровой Preview и веб-экспорт используют LittleJS 1.30.1 с собственным Render3D. Версия закреплена в package.json и lock-файлах. В проекте один графический бэкенд. Физику рассчитывает Rapier с фиксированным шагом 1/60 с, а игровые экраны и HUD отрисовываются в DOM.

Как устроена интеграция

  • В LittleJS камера, список объектов и WebGL-контекст принадлежат экземпляру движка. Скрипт сборки в packages/graphics/device.mjs собирает фабрику устройств из официальной release-сборки и небольшого адаптера. У основного viewport, миниатюр и каждой игровой сессии свои ресурсы. Код фабрики включается в пакет при сборке. Для запуска экспортированной игры достаточно файлов архива.
  • Владелец игрового цикла — сессия Miniforge. Она передаёт время аниматорам LittleJS, обновляет контроллеры и вызывает отрисовку. Компоненты проекта превращаются в EngineObject3D, Mesh и Light3D. Нативный выбор лучом возвращает ID игровой сущности. Трансформации доступны игровым скриптам через SceneNode.
  • У моделей формата glTF/GLB клипы воспроизводятся через GLTFObject. Событие завершения одиночного клипа поступает в редактор правил. Материалы поддерживают текстуры цвета, нормалей и свечения. Ограничения импортёра LittleJS включают morph targets и карты roughness, metalness и occlusion. Загрузчик LittleJS
  • Сетка высот террейна поставляет вершины Render3D и треугольники Rapier. Раскраска ячеек выбирает один из двух материалов. Динамические тела передают мировую позу узлу сцены, включая пересчёт при наличии родителя.
  • Пользовательский фрагментный шейдер определяет mainImage(out vec4 color, vec2 uv), а вершинный — mainVertex(inout vec3 position, inout vec3 normal). Проверка в редакторе компилирует код в том же Render3D, что и игра. Примеры шейдеров находятся в библиотеке редактора.

Скрипты Miniforge

Скрипты Miniforge

Создайте Script в Inspector или импортируйте файл TS/JS через Assets. Назначьте ресурс компоненту Script нужной сущности. Модуль экспортирует фабрику экземпляра. Публичные типы объявлены в packages/runtime/src/types.ts и lifecycle.ts. При работе во внешнем IDE допустим импорт типов, который TypeScript удалит при компиляции. В редакторе контекст называется GameAPI.

export default function (api: GameAPI) {
  let unsubscribe: (() => void) | undefined
  return {
    onStart() {
      unsubscribe = api.events.on('coin.collected', () => {
        api.vars.pickups = Number(api.vars.pickups ?? 0) + 1
      })
    },
    onUpdate(dt: number) {
      api.object.rotation.y += Number(api.params.speed ?? 1) * dt
    },
    onDestroy() { unsubscribe?.() }
  }
}

В Inspector создайте числовой параметр speed. У каждого экземпляра свой словарь api.params. Доступны числа, флаги, строки, цвета, тройки координат и ссылки на сущности или ресурсы по ID.

Проверка записи игрового слота в 3.0.3

Результат await api.saveSystem.save(slot) содержит снимок и два признака записи: localSaved для хранилища устройства и cloudSaved для подтверждённой записи облачным SDK. Событие save.completed приходит при успехе хотя бы одной записи. При полном отказе приходит save.failed с именем слота. Игра может предложить повторить сохранение или скачать снимок. WebSocket и LAN

Запустите Node.js relay из корня репозитория.

node server/relay-server.mjs 8765
curl http://127.0.0.1:8765/health

По умолчанию relay слушает только 127.0.0.1. Для второго ПК в доверенной LAN укажите доступный интерфейс или 0.0.0.0 вторым аргументом, а в настройке клиента используйте IP хоста. Для Web-игры по HTTPS настройте wss:// через TLS-прокси с поддержкой WebSocket Upgrade. /health показывает число подключений и комнат. Комнаты живут в памяти процесса.

api.net.connect({ mode: 'client-server-ws', url, room, token }) возвращает успех после подтверждённого входа в комнату. При отказе используйте getLastError(). Опциональный MINIFORGE_RELAY_TOKEN проверяется при входе и подходит для закрытого теста. Токен, встроенный в открытый клиент, доступен игрокам. Node relay ограничивает комнату 32 участниками по умолчанию, принимает текстовые пакеты до 256 КиБ и ограничивает частоту отправки. settings.multiplayer.maxPlayers пока не задаёт лимит отдельной комнаты на Node или Rust relay.

В экспортированной Desktop-игре хост может включить Auto-start embedded LAN server или вызвать api.net.hostLan({ port, room, gameName }). По умолчанию игра слушает TCP 8765, поиск соседних игр использует UDP 41234. Клиент может прочитать url и room из api.net.discoverLan(1400) или ввести адрес вручную. Встроенный LAN-релей предназначен для локальной сети. Текущий Play with Steam передаёт кадру игровые Steam-команды, поэтому проверяйте нативный LAN API в Desktop-игре.
